一、系统概述
────────────────────────────────────────────────────────────────────

AniVerse 是一个面向二次元角色陪伴场景的交互系统。它将「对话」
「叙事推演」「视觉小说」三种交互模式建立在同一套长期记忆与关系
状态之上，并向下接入番剧内容发现、生成式视觉内容生产、日程提醒
等外部能力。

技术形态：前端 Vue 3 + TypeScript，服务端零第三方依赖 Node，
AI 能力全部对接真实服务（DeepSeek / Cloudflare Workers AI /
AniList GraphQL / 生成式图像服务）。

系统设计目标不是"做一个聊天界面"，而是解决角色陪伴类应用的
三类固有问题：

  · 角色无记忆
    多轮之后人设塌陷、反复提问。
    解法：长期记忆子系统 —— 事实/偏好/事件抽取 → 向量化入库
          → 检索增强生成（RAG）注入上下文。

  · 表现无差异
    永远一张笑脸、永远一个场景。
    解法：情绪状态调度 + 场景语义定位 —— 10 情绪 × 5 姿势立绘、
          25 场景语义切换、融合 CG 演出。

  · 内容无关联
    对话、剧情、番剧各玩各的。
    解法：统一状态中枢 —— 三种交互模式与番剧偏好共享同一份
          角色状态与记忆池，事件可回写。

三、功能详解
────────────────────────────────────────────────────────────────────

3.1 三种交互模式，共用一份状态

  对话交互
    形式：文本 + 图片输入，回复逐字呈现
    模型：记忆检索注入、情绪判断、好感度增减、记忆抽取、
          必要时输出画图指令
    回写：messages / memories / affinity

  叙事推演
    形式：自由描述行动，系统演绎后续
    模型：生成旁白、推进世界状态、产出状态变更摘要
    回写：storyState / memories / affinity

  视觉小说
    形式：立绘 + 对白 + 三选项（含一个明确的低主动选项）
    模型：定情绪、判断场景转移、生成玩家回应候选
    回写：messages / emotion / affinity / 场景

  三种模式共用 store.messages[characterId]、store.memories、
  character.affinity 与 character.emotion，这是跨模式贯通的
  实现基础。

3.2 长期记忆子系统

  · 写入
    每轮对话由模型返回 memory 字段，值得留存的事实写入记忆池
    （source: chat）；叙事推演的关键事件以 source: story 回写；
    用户也可手动补充。

  · 检索（RAG）
    当前输入与最近 39 条记忆共同向量化
    （@cf/baai/bge-m3，1024 维），余弦相似度大于 0.35 的
    Top-3 注入 system prompt。

  · 语义搜索
    独立接口 POST /api/memory/search，返回 {id, score} 列表，
    前端按相关度重排并展示「相关度 54%」；
    向量服务不可用时降级为关键词匹配并明确提示。

  · 治理
    按类型（事实/偏好/事件/羁绊）与重要度（importance）组织；
    记忆条数与角色卡计数保持一致，支持增删改。

3.3 番剧内容发现子系统（重点模块）

  面向"我想看点什么样的番"这一真实需求设计，数据基座为
  AniList GraphQL（单一数据源，服务端统一做字段裁剪与结构归一）。

  ■ 能力矩阵

    推荐流
      POPULARITY_DESC + isAdult:false，取 12 部，
      输出封面 / 评分 / 类型 / 集数 / 放送时间。

    本季放送日历
      抓 status: RELEASING 共 50 部，按 nextAiringEpisode.airingAt
      归入周一至周日；"今天"按 UTC+8 计算，与服务器时区无关，
      默认停留在该天。

    混合语言搜索
      SEARCH_MATCH 直搜；中文关键词命中不足 3 部时，
      先经译名服务转成原名二次检索，按 id 去重合并。

    描述式 AI 推荐
      见下方「三段式检索 + 二次生成」流程。

    标题本地化
      批量译名接口（单次不超过 40 条），前端缓存结果，
      避免重复请求。

    追番清单
      收藏进 watchlist，含状态（想看/在看/看过）与追番进度，
      随本地状态持久化。

    外链溯源
      每部作品提供 AniList / MyAnimeList / Bangumi 站内搜索跳转。

  ■ 描述式 AI 推荐（本模块的重点设计）

    普通"AI 推荐"的通病是模型凭空编片名。
    本系统采用「先检索、再生成」的两阶段方案：

      用户描述（如"想看点轻松治愈、有点恋爱线的番"）
            ↓
      ① 结构化
         模型输出 { keyword(英/日), genre(AniList 枚举),
                    reason, reply }
            ↓
      ② 三级检索（数据必须真实）
         a. keyword 为拉丁字符 → SEARCH_MATCH 精确检索
         b. 无结果 → 按 genre 取热门
         c. 仍无结果 → keyword 走 POPULARITY_DESC 兜底
            ↓
      ③ 二次生成
         把真实候选（片名/类型/评分）回灌给模型，
         生成 80~160 字自然推荐语，
         不允许出现检索结果之外的作品
            ↓
      前端先展示一句人话开场，再渲染卡片，
      每张卡片可一键加入追番清单。

    这样既保留了自然语言交互的体验，又保证推荐内容
    可溯源、不虚构。

  ■ 现状说明
    番剧详情弹窗的剧情简介与评分来源标注仍为示例文案，
    接入 AniList description 的改造已列入待办（见「已知限制」）。

3.4 情绪与场景表现层

  · 情绪调度
    每轮先随机抽取一个情绪倾向写入提示词（避免表情固化为
    "温柔微笑"），最终情绪由模型结合上下文裁定；
    用户明显冷淡时禁止判定为「开心大笑」等高唤醒情绪。
    10 种情绪 × 5 个姿势 = 50 张透明立绘（C001–C050），
    按情绪分组轮换姿势。

  · 场景语义定位
    25 个场景各配语义描述并向量化，与对话文本计算余弦：
      大于 0.60：立即切换
      大于 0.40：进入候选，需连续 2 轮一致，
                 且距上次切换不少于 2 轮（滞回防抖）
      模型给出的合法场景：作为第二候选

  · 融合 CG 演出
    35% 概率将背景替换为当前场景的融合 CG（F01-1 … F25-2），
    隐藏立绘，持续 2~3 轮后退出。

3.5 生成式视觉内容管线

  ■ 三个入口

    对话内手动
      输入框工具栏 ✨ 按钮，或直接说"画张画"
      产出：生成图入对话 + 自动入图库

    对话内自主
      模型输出 [DRAW]画面描述[/DRAW]，
      服务端剥离标记并返回 drawPrompt
      产出：同上，附带生成状态提示

    图库在线工作台
      我的图库 → 右上角「在线生图」
      产出：完整参数面板，支持批量

  ■ 工作台参数

    模式      文生图 / 图生图（需上传参考图）
    画面比例  AI 自动（模型裁定）/ 9:16 / 16:9 / 1:1 /
              3:4 / 4:3 / 21:9 / 自定义 宽:高（各 1~32）
    张数      1 / 2 / 3 / 4
    画质      精致 / 标准 / 快速
    风格      鲜明 / 自然
    背景      实心 / 透明
              （返回真 alpha，落库时转 WebP 保留透明通道）
    提示词    手写，或「AI 润色」扩写；
              可开启「生成前自动润色」

  ■ 工程处理
    生成结果先压缩（长边 1024，实心 → JPEG，透明 → WebP），
    再按目标比例校验（偏差大于 6% 时居中裁切并标注），
    最后同时写入对话流与图库，
    并提供「下载原图（未压缩 PNG）」。

3.6 支撑能力

  · 角色与人格管理
    创建流程收集名字/称号/小传/性格标签/语气，
    拼装为 personaPrompt 真正进入系统提示词；
    运行期可在聊天页随时编辑，下一轮即生效。

  · 关系状态派生
    好感度 → 关系阶段（陌生 0 / 熟悉 25 / 亲近 50 / 心动 75），
    数值变化跨越阶段时给出状态提示，
    避免"数值涨了但等级不动"。

  · 日程提醒服务
    自然语言解析（文本 → {title, dueAt, repeat}），到点提醒；
    每日/每周提醒在触发后顺延至下一次，而非一次性销号。

  · 运行观测面板
    角色数、对话条数、记忆条数、平均好感度、消息情绪光谱
    均由真实状态计算；趋势图与领域事件流为架构示意，界面已标注。

  · 沉浸式大厅
    three.js 星轨宇宙 + 自定义后处理（暗角/颗粒/色散）
    + 记忆节点 HUD 投影，支持移动端。

  · 使用声明
    首次进入站点弹出声明弹窗（课程学习用途、内容虚构、
    数据存于本地、第三方版权归属），
    确认后写入本地标记，不再重复打扰。

3.7 全站音乐播放器

  · 三级渐进交互
    一级：圆形按钮，当前封面做圆形裁切，外圈是 SVG
    环形进度（随播放进度推进，跨页面同步）；
    二级：点击后向下弹出方形面板，含封面、歌名、
    歌手、上一首/播放暂停/下一首、可拖动进度条；
    三级：默认折叠的搜索入口，展开后是搜索框
    + 3 条结果，点结果即刻播放并自动收起。

  · 内置离线歌单
    随站点分发 10 首《塞壬唱片》精选曲目
    （mp3 + 封面 + playlist.json），首屏即加载、
    首曲音源预挂好，点播放零延迟，放完自动续播；
    歌单由脚本按热度与可播性检索、探测后生成。

  · 搜索点播
    服务端把多组查询合并去重，按歌名相似度、
    歌手/厂牌命中、热度打分，并并行探测前 5 首的
    可播性，优先返回能播的；需要会员的标 VIP 角标。
    厂牌名做双向包含匹配，避免只按歌名匹配搜不到。

  · 播放与位置适配
    audio 是模块级单例，切页面不中断；
    进度条支持按下定位与拖动跟随，
    元数据未就绪时暂存拖动量、加载完补上。
    普通页面嵌在顶栏；首页默认与导航文字同一水平线，
    下滚 64 像素后钉到左上角常驻，滚回顶部自动归位。

5.3 核心链路

① 对话链路（POST /api/chat/turn）

   用户输入
     ├─ cleanHistory：最近 24 条，仅保留 role / content
     └─ relevantMemories：query + 最多 39 条记忆 → 向量化
        → 余弦 > 0.35 → Top3
            ↓
   system prompt = 人格 + 情绪准则 + 记忆块 + 画图规则
                   （要求仅输出 JSON）
            ↓
   DeepSeek（4 组参数变体依次重试，任一成功即返回）
            ↓
   parseModelJson：直接解析 → 剥离 json 围栏 → 抠首尾大括号
            ↓
   仍失败 → inferFields：正则推断
            reply / emotion / scene / affinityDelta
            ↓
   返回 { reply, emotion, affinityDelta, memory, drawPrompt }
            ↓
   前端：占位气泡 → 每 24ms 补 2 字 → 合并落盘（600ms 防抖）

② 视觉小说链路（POST /api/galgame/turn）

   抽取情绪倾向 → 写入提示词（"本轮情绪倾向：困倦打哈欠"）
            ↓
   模型返回 { reply, emotion, scene, affinityDelta,
             suggestions[3] }
            ↓
   情绪：模型合法值 → 台词关键词 → 随机兜底
        （冷淡输入禁止高唤醒情绪）
   场景：对话向量 × 25 条场景描述 → 大于 0.60 立即切换；
        大于 0.40 需连续 2 轮 + 冷却 2 轮；
        模型给值作第二候选
   选项：不足 3 条时调用独立生成器；
        第 3 条强制为低主动项（正则校验 + 模板兜底）
            ↓
   前端：立绘按情绪切组、portraitSeed+1 换姿势、
        35% 概率进入 CG 演出

③ 番剧推荐链路（POST /api/catalog/ai-recommend）

   用户自然语言描述
            ↓
   ① 结构化：模型输出 { keyword, genre, reason, reply }
            ↓
   ② 三级检索（保证内容真实）
      a. keyword 为拉丁字符 → SEARCH_MATCH 精确检索
      b. 无结果 → 按 genre 取热门
      c. 仍无结果 → keyword 走 POPULARITY_DESC 兜底
            ↓
   ③ 二次生成：真实候选（片名/类型/评分）回灌模型
      → 80~160 字推荐语
            ↓
   前端：一句人话 + 卡片列表；
        卡片可收藏进追番清单，可跳 AniList / MAL / Bangumi

④ 生成式图像链路（POST /api/image/generate）

   参考图优先级：
     图生图 data URL > 指定路径 > 空白画布（文生图现场生成 PNG）
            ↓
   上游仅提供 /images/edits（/images/generations 不可用），
   必须携带一张 image
            ↓
   返回 base64 PNG（通常 2~4 MB）
            ↓
   前端压缩：长边 1024；实心 → JPEG(0.86)，透明 → WebP(0.92)
            ↓
   比例校验：与请求比例偏差大于 6% 时居中裁切并标注
            ↓
   落库：对话消息 + store.assets（source: AI 生图）+ localStorage

5.4 关键设计决策

  · 模型 JSON 输出不稳定
      （启用 json_object 约半数返回空白）
    处理：提示词约束 JSON + 宽松解析 + 关键词兜底
          + 4 组参数变体重试
    依据：兜底后用户始终能获得可继续的回应，不出现错误弹窗

  · 关闭 thinking 反而返回空内容
    处理：统一 thinking: enabled + reasoning_effort: low
    依据：实测该组合最稳定

  · 图像上游仅支持编辑（图生图）
    处理：服务端以 zlib + 手写 PNG chunk 生成空白画布作为底图
    依据：文生图无需真实参考图即可工作

  · 本地存储约 5 MB，而单张生成图为 2~4 MB
    处理：生成图先压缩；落盘设预算（消息 2.4 MB / 图库 1.2 MB），
          超限丢弃最旧图片并标记
    依据：规避配额超限导致后续所有消息静默写入失败

  · 逐字动画每 24ms 触发一次状态变更
    处理：$subscribe 合并落盘（600ms 防抖）
          + 生成期间暂停写入 + pagehide 兜底
    依据：原实现单次回复触发 72 次全量序列化

  · 场景切换抖动
    处理：语义阈值 + 连续 2 轮一致 + 冷却 2 轮
    依据：单轮余弦相似度噪声过大

  · 静态素材总体积 230 MB
    处理：gzip 传输 + immutable 长缓存；
          首屏只加载当前场景与立绘
    依据：未压缩时单个 vendor-three 需传输 558 KB

  · 记忆条目增多后 RAG 反而失效
    处理：query + 39 条记忆 = 40（向量单请求上限）
    依据：原实现上限写死 40，记忆 40 条以上时检索恒为空

  · 模型偶发空回复
    处理：提示词润色与比例裁定各重试 3 次
    依据：同型号模型的已知缺陷

七、部署
────────────────────────────────────────────────────────────────────

运行环境

  · 访问地址    http://106.54.202.104
                （建议后续接入域名与 HTTPS）
  · 运行环境    Linux，Node v20.18.1
                （安装于 /opt/node，不在系统 PATH）
  · 服务目录    /opt/aniverse
  · 监听配置    HOST=0.0.0.0  PORT=80（直接对外，未前置 nginx）
  · 进程形态    setsid nohup /opt/node/bin/node --env-file=.env
                server/index.mjs > app.log 2>&1

  服务器凭据与 .env 密钥见内部交接文档，不写入本仓库。

标准发布流程

  cd <项目>\frontend
  npm run build        1. 构建（含 vue-tsc 类型门禁）
  python mkzip2.py     2. 打包 dist + server + .env + README + start.py
  node deploy5.mjs     3. 上传 → 解压 → 修正 .env → 重启 → 健康检查

deploy5.mjs 执行的实际步骤

  SFTP 上传 zip 至 /opt/aniverse/app.zip
  cd /opt/aniverse && rm -rf dist server && unzip -o -q app.zip
  sed -i '/^HOST=/d;/^PORT=/d' .env
  printf 'HOST=0.0.0.0\nPORT=80\n' >> .env
  pkill -f 'server/index.mjs' && sleep 1
  setsid sh -c 'nohup /opt/node/bin/node --env-file=.env
                server/index.mjs > app.log 2>&1 < /dev/null &'
  curl -s --max-time 5 http://127.0.0.1/api/health

易错点：发布包 .env 覆盖线上配置

  发布包携带的是本地 .env（HOST=127.0.0.1 PORT=8787），
  解压会覆盖服务器上正确的 HOST=0.0.0.0 PORT=80，
  表现为外网无法访问、服务仅监听本地。

  deploy5.mjs 已内置修正步骤；手工部署必须自行补齐：

    cd /opt/aniverse
    sed -i '/^HOST=/d;/^PORT=/d' .env
    printf 'HOST=0.0.0.0\nPORT=80\n' >> .env

上线验证

  curl.exe -sS http://106.54.202.104/api/health
  期望：{"ok":true,"model":"deepseek-flash","configured":true}

  静态资源（gzip 与长缓存）：
  curl.exe -sS -o NUL -D - -H "Accept-Encoding: gzip"
           http://106.54.202.104/assets/<hash>.js

运维命令

  pgrep -af server/index.mjs        查看进程
  tail -f /opt/aniverse/app.log     查看日志
  pkill -f 'server/index.mjs'       停止服务
  cd /opt/aniverse && setsid sh -c \
    'nohup /opt/node/bin/node --env-file=.env server/index.mjs \
     > app.log 2>&1 < /dev/null &'   启动服务

部署注意事项

  · 发布包约 238 MB（素材占主要体积），上传需数分钟属正常现象
  · 不要用 PowerShell Compress-Archive 打包：会写入反斜杠路径，
    Linux 解压失败，必须使用 mkzip2.py
  · 后续若前置 nginx：反向代理 80 → 127.0.0.1:8787，
    .env 改回 HOST=127.0.0.1，并对 /api/image/* 增加限流
  · 当前为 nohup 托管，服务器重启不会自动恢复，
    建议后续接入 systemd / supervisor

九、已知限制
────────────────────────────────────────────────────────────────────

  1. 状态仅存于浏览器本地：换设备或清理缓存即归零。
     若要演进为服务端记忆，需迁移 store
     （服务器 Node 20 无内置 node:sqlite，
      可选 better-sqlite3 或升级至 Node 22+）。

  2. 素材已转 WebP：245 MB PNG → 43 MB（大图 + 缩略），
     原始 PNG 保留在 assets-src/，不进部署包，
     可用 scripts/build-images.py 重新生成。

  3. 图像上游仅支持图生图：文生图以空白画布兜底；
     上游未开放 2K/4K 放大接口，故未提供。

  4. 番剧详情弹窗的简介与评分来源为示例文案，
     尚未接入 AniList 真实 description 字段。

  5. 番剧接口无服务端缓存：每次进入番剧页会触发一次推荐
     与一次日历查询，弱网下首屏偏慢。

  6. /api/* 未做鉴权：公网可直接调用并消耗凭据额度，
     建议增加 token 与限流。

  7. 观测面板的趋势图与事件流为示例数据（界面已标注），
     其余指标为真实统计。

  8. 音乐依赖第三方非官方接口：搜索与音源解析无 SLA、
     随时可能失效；需要会员或已下架的曲目无法播放
     （列表中标 VIP）。内置 10 首随站点分发，不受影响。


十、项目约定
────────────────────────────────────────────────────────────────────

  1. 不得删除 assets-src/ 下的原始素材
     （立绘、CG、场景为长期生成成果，删除需重新生成；
       public/ 下是对应的 WebP 派生图）
  2. .env 与服务器凭据不入库、不进对话
  3. UI 变更前先截图留档，变更后逐项比对
  4. 后端改动先执行 node --check server/index.mjs，再重启服务
  5. 视觉与文风约定：不混用美术风格、场景统一 16:9、
     角色立绘保持透明底、回复避免模板化的正能量表达
